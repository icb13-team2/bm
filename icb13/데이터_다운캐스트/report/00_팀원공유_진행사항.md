# 쇼핑 라벨링 데이터 정리 진행사항 (팀원 공유용)

작성일: 2026-10-12 · 정리: 깡총 · 폴더: `데이터_다운캐스트/`
원문 문장은 이 문서에 넣지 않았어요. 열 이름과 숫자만 적었어요.

## 한 줄 요약

JSON 7개(468.7MB)를 parquet 한 파일(14.1MB)로 줄였고, 분석하기 좋은 tidy 표 3개도 만들었어요.
분석은 아래 3개 tidy 표부터 시작하면 돼요.

## 1. 지금까지 한 일

| 순서 | 한 일 | 결과 |
|---|---|---|
| 1 | JSON 7개를 합침 (AS, 결제, 교환, 반품, 배송, 업무처리, 주문) | 895,071행 × 15열, 대화 26,270개 |
| 2 | downcast | 문장번호를 `uint16`으로, 나머지는 `string[pyarrow]`로 바꿈. 메모리 814.5MB → 222.0MB |
| 3 | category 변환 | 문자열 14개 열 모두 category로 바꿈. 메모리 92.9MB (원본 대비 89% 감소) |
| 4 | 압축 방식 7종 비교 | brotli-11이 가장 작았지만 저장이 3분 넘게 걸림 |
| 5 | 최종 파일을 zstd-19로 저장 | 14.1MB. brotli-11(13.9MB)과 거의 같고 저장이 훨씬 빠름 |
| 6 | 값 검증 | 압축 방식마다 다시 읽은 값이 원본과 전부 같음 |
| 7 | tidy(long form) 3개 표로 분리 | 아래 표 참고 |
| 8 | 카테고리 값 정리 | 15개로 보이던 값이 7개로 정리됨 (끝 공백, `as` → `AS`) |
| 9 | 기술 통계 작성 | 수치형·범주형 모두 03번 보고서에 있음 |

### 파일 크기 비교

| 단계 | 크기(MB) |
|---|---:|
| 원본 JSON 7개 (압축 해제) | 468.7 |
| 원본 zip | 33.4 |

| parquet: category (snappy) | 28.4 |
| **parquet: category (zstd-19) ← 기준 파일** | **14.1** |

### 만든 tidy 표

| 표 | 한 행의 뜻 | 행수 | 크기(MB) | 주요 열 |
|---|---|---:|---:|---|
| `tidy_dialogs_zstd3.parquet` | 대화 1건 | 26,270 | 0.19 | 대화셋일련번호, 카테고리, 총턴수, 발화수, 고객발화수, 상담사발화수 |
| `tidy_utterances_zstd3.parquet` | 발화 1줄 | 895,071 | 12.96 | 대화셋일련번호, 문장번호, 화자, QA, 발화, 의도, 보조의도, 의도기준 |
| `tidy_entities_zstd3.parquet` | 발화 안의 값 1개 | 2,840,965 | 6.74 | 대화셋일련번호, 문장번호, 출처, 값, 유형 |

- `발화`: 원래 4개 열(고객질문, 상담사질문, 고객답변, 상담사답변)에 나뉘어 있던 걸 하나로 합쳤어요. 모든 행에 값이 정확히 1개였어요.
- `의도`: 고객의도·상담사의도 2개 열을 하나로 합쳤어요. 화자와 같은 쪽 열을 써요(고객 발화는 고객의도, 상담사 발화는 상담사의도). 어느 열을 썼는지는 `의도기준`(화자일치열 / 반대열 / 없음)에 남겼어요. 두 열이 동시에 있던 2,803행은 버려지는 쪽 값을 `보조의도`에 보존했어요.
- `tidy_entities`: 개체명·지식베이스·용어사전을 쉼표로 풀어서 한 줄에 값 하나로 만들었어요.
- `도메인` 열은 값이 K쇼핑 하나뿐이라 뺐어요.

### 알아둘 숫자

- 대화당 총턴수: 평균 34.07, 중앙값 32, 90% 52, 95% 58, 99% 74, 최대 298
- 카테고리별 평균 턴수: 결제 38.8 > 배송 37.2 > 교환 36.1 > 주문 33.0 > 반품 32.2 > 업무처리 30.0 > AS 27.1
- 의도가 비어 있는 발화: 414,084행 (46.3%)

## 2. 아직 남은 일

1. **의도 합치기 규칙 (정함)**: 두 열이 동시에 있는 행이 2,803행(0.3%)이에요. 화자 일치 열을 `의도`로 쓰고, 나머지는 `보조의도`에 남겼어요. 반대 열만 있는 행(고객 51행, 상담사 676행)은 `의도기준`이 `반대열`이에요. 모델에 넣기 전에 `반대열` 행을 쓸지만 정하면 돼요.
2. **개체 쉼표 분리 확인**: 값 안에 쉼표가 들어 있는 경우가 있으면 잘못 쪼개졌을 수 있어요. 표본 검수가 필요해요.
3. **의도 빈 칸 처리**: 의도가 빈 발화가 46.3%예요. 앞 발화의 의도로 채울지, 그대로 둘지 정해야 해요.
4. **분석 시작**: 턴수가 길어지는 트리거 찾기를 tidy 표에서 시작해요.
5. **AI-Hub 이용약관 확인**: 원문을 외부로 보내는 작업을 하기 전에 아직 확인이 안 됐어요.

## 3. 팀원이 알아야 할 결정

| 결정 | 이유 |
|---|---|
| 기준 파일은 zstd-19 | brotli-11과 크기가 거의 같고 저장 속도가 훨씬 빠름 |
| 다시 저장하는 중간 파일은 zstd-3 | 저장이 1~2초라 분석하면서 자주 저장해도 부담이 적음 |
| 기준 파일(`shopping_02_category_zstd-19.parquet`)은 덮어쓰지 않기 | 모두가 같은 원본에서 시작해야 결과가 같음 |
| 의도는 화자 일치 열 우선, 버려지는 값은 `보조의도`에 보존 | 고객 우선으로 하면 상담사 발화 1,539행에 고객 쪽 의도가 붙어 틀려짐. 값을 잃지 않아야 JEV·EDA를 다시 해도 안전함 |
| 빈 문자열은 NaN으로 바꾸지 않음 | "해당 없음"이라는 뜻이라서 |
| 원문 열에 `.str`을 쓰려면 먼저 string으로 바꾸기 | category는 문자열 처리용이 아님. `src/load_data.py`의 `load_shopping()`이 자동으로 바꿔 줌 |
| 보고서·공유 문서에는 원문을 넣지 않기 | 라벨, ID, 숫자만 사용 |

## 4. 바로 쓰는 법

`데이터_다운캐스트/` 폴더에서 실행해요.

```python
import pandas as pd

# 턴수·흐름 분석 (원문 열 없이 가볍게)
dia = pd.read_parquet("./data/tidy_dialogs_zstd3.parquet")
dia.groupby("카테고리", observed=True)["총턴수"].describe()

utt = pd.read_parquet(
    "./data/tidy_utterances_zstd3.parquet",
    columns=["대화셋일련번호", "문장번호", "화자", "의도", "의도기준"],
)

# 원문 컬럼이 필요할 때 (.str 사용 가능)
from src.load_data import load_shopping
df = load_shopping()
```
